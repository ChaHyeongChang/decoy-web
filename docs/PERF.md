# 렌더링 성능 (120Hz 대응)

렌더링 최적화(2026-10-13~, PR #19 · #20)의 목표 · 재는 법 · 전후 수치다. 결정과 이유는 `docs/DECISIONS.md` 7절, 사람이 실기기에서 확인할 것은 `docs/HUMAN_CHECKS.md` '렌더링 최적화' 절.

## 1. 목표

| 기기 | 목표 | 프레임 예산 |
|---|---|---|
| 120Hz 화면의 고사양 휴대폰 · PC | 120fps | 8.33ms |
| 중급 휴대폰 | 60fps 안정 | 16.7ms |
| 저사양 휴대폰 | 30fps 이상 | 33.3ms |

- 게임 규칙 · 판정 · 정보 차단, 서버 틱 30Hz · 스냅샷 20Hz는 바꾸지 않는다. 화면 프레임만 빨라진다
- "높음" 품질의 그림은 눈에 띄게 바뀌지 않는다(전후 스크린샷 `artifacts/perf/`)
- 프레임 제한 설정: **자동**(화면 주사율을 따른다, 기본) · **60**(배터리 절약) · **120** · **절반**(잔렉 고치기). 목표는 늘 화면 주사율의 약수다(144Hz에 60 → 72, 6절)

## 2. 휴대폰에서 재는 법 (`?debug=1`)

1. 휴대폰 **크롬 탭**에서 게임 주소 끝에 `?debug=1`을 붙여 연다. 예: `https://<서비스 주소>/?debug=1`. 배포 빌드(Render)에서도 켜진다. 홈 화면에 설치한 앱(PWA · TWA)은 주소창이 없어 주소를 바꿀 수 없으니 크롬 탭에서 연다(같은 게임 · 같은 렌더링이다)
2. 디버그 오버레이가 뜬다. 휴대폰(터치)에서는 HUD를 가리지 않게 한 줄짜리 접힌 칩으로 시작하고, 칩을 누르면 펼쳐지고 다시 누르면 접힌다. PC에서는 펼친 채로 시작한다(0.25초마다 갱신)
3. 펼친 화면에 한 번에 보이는 것

| 항목 | 뜻 |
|---|---|
| FPS · 목표 · 화면 Hz · 제한 | 최근 1초에 그린 프레임 수, 지금 목표 FPS(화면 주사율의 약수 — 82.5처럼 소수일 수 있다), 잰 화면 주사율, 프레임 제한 설정(자동 · 60 · 120 · 절반) |
| 프레임 평균 · p95 · 늦음 · 넘김 | 그린 프레임 사이 간격의 평균과 95번째 백분위(느린 쪽 5%), 최근 1초 늦은 프레임 비율(간격 ≥ 목표 주기 + 반 vsync — rAF가 vsync를 건너뜀), 넘김(rAF 시각부터 그리기를 마칠 때까지 + 1ms가 한 vsync보다 긴 프레임 — 크롬은 다음 rAF에 같은 격자 시각을 줘 FPS · 늦음에는 안 나오지만 그 프레임은 한 칸 늦게 보인다. 0이나 100%에 가까우면 고르다) |
| 작업 평균 · p95 · 안개 p95 | 한 프레임에 게임이 메인 스레드에서 쓴 시간(갱신 + 그리기 명령), 안개 주기 프레임(1초에 20번 빛 지도를 다시 칠하는 프레임)만의 p95 |
| 핑 | 서버와의 왕복 지연 |
| 서버 틱 · 스냅샷 | 마지막으로 받은 서버 틱 번호와 받은 스냅샷 수 |
| 예측 오차 | 내 캐릭터 예측과 서버 결과의 최근 보정 거리(타일)와 아직 확인받지 못한 입력 수 |
| 그리기 · 건너뜀 | 한 프레임의 WebGL 그리기 호출 수 (Canvas 렌더러면 그린 객체 수). 건너뜀은 프레임 제한 · 판 밖 30fps 때문에 그리지 않고 넘긴 화면 갱신(rAF)의 누적 수 — 제한 60 · 120Hz 화면이면 초당 약 60씩 늘고, 제한이 화면 주사율과 같으면 늘지 않는다 |
| 품질 | 지금 품질 단계와 정한 곳 · 자동 조정 상태 |
| DPR | 기기 픽셀 배율과 캔버스 백버퍼 크기 |

4. 봇과 연습이나 온라인 판을 1~2분 하면서 숫자를 본다. 처음 5초는 시작 비용이라 무시한다

## 3. 컨테이너에서 재는 법 (`npm run perf:frame`)

`tests/perf/`: 봇과 연습 판을 크롬에서 돌려 프레임마다 잰다. 화면 코드가 아니라 브라우저 API에 끼운 훅(`perfHooks.ts`)으로 재므로 최적화 전 빌드도 같은 방법으로 잰다.

```sh
npm run perf:frame                                  # 이 저장소 빌드 → artifacts/perf/current/frame-perf.json
DECOY_PERF_DIR=<빌드한 다른 checkout> DECOY_PERF_LABEL=before \
  npx playwright test --config tests/perf/playwright.config.ts   # 다른 빌드 (예: origin/main)
```

- CPU 느리게: CDP `Emulation.setCPUThrottlingRate` (렌더러 메인 스레드만. GPU 프로세스는 그대로)
- 120Hz: 헤드리스 크롬은 화면 갱신이 60Hz로 묶여 플래그로 풀리지 않는다 → rAF를 120Hz로 직접 돌린다(합성기는 60Hz로 내보내지만 게임은 120번 걷는다)
- 이 컨테이너에는 GPU가 없어 WebGL을 SwiftShader(CPU)가 칠한다. WebGL 장면의 전달 FPS는 실제 휴대폰과 상관이 없고, **메인 스레드 작업 시간 · 그리기 호출 · 텍스처 올리기 · 할당**이 의미 있는 값이다. 2D 캔버스도 CPU로 칠하게 하고(`--disable-accelerated-2d-canvas`) `?scale`로 백버퍼를 줄여 래스터가 프레임을 막지 않게 한다
- Canvas 렌더러 장면은 메인 스레드가 화면까지 칠하므로 전달 FPS도 뜻이 있다
- 수치는 기계마다 다르다. 전후는 같은 기계에서 번갈아 잰다

### 5.1 재는 법 (`tests/perf/motion.spec.ts`)


- 같은 경로: 봇을 묶고(연습) 열린 바닥 y 16.5에서 x 28.5 → 오른쪽 1.8초 · 왼쪽 1.8초 × 3(카메라가 맵 끝에 막히지 않는 자리, 괴물은 위를 보고 걸어 앞당김이 가로로 밀지 않게). 키를 누른 뒤 0.7초(따라가기 τ 0.12초의 약 6배)부터 뗄 때까지만 센다
- 프레임마다(판 장면이 실제로 그린 프레임만 — 프레임 제한이 건너뛴 rAF는 빼고) ① 내 그린 자리(`getRenderPos`) 변화량 ② 카메라 이동량(화면 위 타일 (0,0) 자리) ③ 카메라 기준 화면 위 내 자리(그린 내 엔티티의 `tileToClient`)를 기기 px로 적는다(`motionHooks.ts` — 두 빌드에 다 있는 디버그 훅만 쓴다)
- 장면: Canvas 낮음 960×540(메인 스레드가 화면까지 칠해 전달 FPS가 뜻이 있다), 휴대폰 915×412@2.625, WebGL 휴대폰 중간(SwiftShader, 백버퍼 0.4배). 60Hz는 브라우저 rAF, 120Hz는 직접 돌리는 rAF(vsync 시각을 준다). 90fps = 120Hz에서 30%의 프레임이 9ms 더 걸려 vsync를 놓침(8.3 · 16.7 · 25ms가 섞이고 입력 타이머 · 기기 안 서버 틱도 늦게 깬다). - 지표: ① 비율 = 프레임당 이동 ÷ (구간 평균 빠르기 × 그 프레임 간격) — 1이면 고르다, 0.5 미만 멈칫 · 1.5 넘게 튐. ① 변동 계수는 간격으로 나누지 않은 프레임당 이동의 표준편차 ÷ 평균(간격이 고르지 않으면 커진다). ③ 변화는 프레임당 화면 위 내 자리 변화(같은 빠르기로 따라가면 0이어야 한다), ③ 폭은 구간 안 최대 − 최소. 화면 지연 = 그린 자리가 예측 상태보다 뒤인 시간(틱 사이 보간이 더하는 지연). 첫 움직임 = 키 눌림(페이지 시계) → 그린 자리가 처음 움직인 프레임이 끝난 시각, 32번(누르기 전 기다림을 바꿔 입력 틱 위상을 섞는다) — 1e-3타일(기기 약 0.1px)과 보이는 1px 둘

### 6.1 크롬은 늦은 프레임의 rAF 시각을 어떻게 주나 (이 컨테이너 크롬 실험)

- 그러나 화면에 보이는 시각은 프레임이 끝난 뒤의 vsync라, 작업이 주기를 넘나들면 '계산한 시각 → 보인 시각' 차이가 프레임마다 달라진다. 이것을 가상 시계의 작업 시간 모형(`tests/helpers/virtualClock.ts` work)으로 흉내 낸다

- 가상 시계(rAF를 직접 돌림)에 **작업 시간 모형**을 더했다(`tests/helpers/virtualClock.ts` work): 그린 프레임마다 작업 시간(주기의 배수)을 정하고, 6.1절의 크롬 규칙대로 vsync를 넘긴 프레임 다음 rAF는 같은 격자 시각으로 늦게 시작(늦음이 한 주기를 넘으면 칸을 건너뜀), 타이머도 메인 스레드가 바쁜 동안 미뤄진다. **화면 표시 = 작업이 끝난 뒤 첫 vsync**. 그래서 헤드리스 크롬(60Hz)에서도 60~240Hz의 실제 표시 시각을 같은 빌드면 같은 수로 잰다
- 부하 넷: 고름(작업 0.35주기) · 꾸준히 모자람(0.95주기 ± 30% — 144Hz에서 약 130fps, 사용자 PC '100fps 넘는데 끊김'의 모형) · 안개 프레임만 넘침(안개를 다시 그린 프레임 1.4주기) · 가끔 튐(25% 프레임 1.5주기)
- 장면: 주사율 60 · 75 · 100 · 120 · 144 · 165 · 240Hz × 부하 넷(1920×1080@1 품질 높음), 창 크기(1920×1080 · 2560×1440 × DPR 1 · 1.25 · 1.5 — 창 = 모니터 ÷ DPR, 품질 높음 / 휴대폰 800×360@3 · 915×412@2.625 · 640×360@2, 품질 중간) × 고름 · 꾸준히 모자람, 괴물, 고정 제한 60(75 · 100 · 144 · 165Hz) · 120(144 · 165Hz), 격자 맞춤 끄기(`?camSnap=0`), WebGL(SwiftShader — GPU 안개 경로: 60 · 144Hz PC, 120Hz 휴대폰, 괴물)
- 경로: 봇과 연습(봇 묶음), 판 시작 뒤 16.5초 서 있다가(적응형이 정할 시간: 예열 5초 + 지속 10초) 열린 바닥 y 16.5에서 오른쪽으로 1.8초 걷는다. 키를 누른 뒤 0.7초부터 뗄 때까지 센다. 입력 반응은 서 있다가 12번 눌러 '키 → 그린 자리가 처음 움직인 프레임이 화면에 표시된 vsync'
- 지표(기기 px = 백버퍼 px): ① 비율 = 프레임당 그린 자리 변화 ÷ (빠르기 × rAF 간격) ② 카메라 프레임당 이동(값:개수) ③ 화면 위 내 자리 폭 ④ rAF 간격 · 표시 간격 변동 계수 · **표시 ≠ 계산 프레임 %**(보인 프레임 간격과 계산 시각 간격이 반 주기 넘게 다른 프레임 — 이만큼 걸음이 덜컥인다) · 표시 지연(rAF 시각 → 표시 vsync) ⑤ **시야 빛 − 몸 폭**(이 렌더러가 그린 빛 중심 = 안개 주기 눈 + 실제로 옮긴 양). 표시 vsync마다 보이는 프레임으로 **맵 스크롤 어긋남**(같은 빠르기면 맵은 표시 시각에 비례해 움직여야 한다 — 그 직선과의 차)과 **시야 빛 어긋남**(빛 − 몸이 평균에서 벗어난 양)
- 전 = `origin/main` ea25bcf(PR #24 병합)를 따로 빌드해 같은 컨테이너에서 잼(`artifacts/perf/pacing/before`), 후 = 이 브랜치(`after`)

### 6.3 전 → 후 (걷기 · 카메라 · 입력)

전 = `origin/main` ea25bcf(PR #24 병합), 후 = 이 브랜치 최종 빌드. 표의 px는 백버퍼 px(기기 px)다. '-'는 그 빌드에 없는 장면(격자 끄기는 고친 뒤 빌드의 진단 옵션)이다.

**읽는 법**
- **주사율보다 조금 모자란 fps('sustained', 0.95~1.25 vsync).** 전에는 목표가 화면 주사율에 남아 rAF 간격 변동 계수가 0.26~0.29이고, 보인 프레임의 18~24%가 계산 시각과 한 주기 어긋났다. 후에는 사다리 칸(144 → 72, 165 → 82.5, 120 → 60, 100 → 50, 240 → 120)으로 내려가 간격 · 표시가 모두 한 값이다. 변동 계수 0, 어긋남 0%, 표시 지연은 한 값(예: 144Hz 13.9~20.8 → 13.9ms)이다. 60 · 75Hz는 60 이상 약수가 없어 그대로다(품질 하향은 이 모형의 작업 시간을 줄이지 않는다)
- **고정 제한.** 전에는 60 · 120이 평균만 맞춰 간격이 섞였다(변동 계수 0.16~0.35). 후에는 가장 가까운 약수로 고르다: 144 · 165Hz의 120 → 제한 없음, 144Hz의 60 → 72, 165Hz의 60 → 55, 75Hz의 60 → 75, 100Hz의 60 → 50. 맵 스크롤 어긋남 p95도 2.3~5.0 → 0.5~3.2px로 줄었다
- **시야 빛 − 몸 폭(⑤).** WebGL(GPU 안개) 장면은 13~23px → 1px, 시야 빛 어긋남 p95는 6.4~10 → 0.5px다. Canvas 장면은 Canvas 합성이라 따라가지 않아 그대로다(15~30px — 품질 낮음 · Canvas 렌더러에 남는 몫, HUMAN_CHECKS)
- **'안개 프레임만 넘침' · '가끔 튐'.** 그대로다. 크롬이 늦게 끝난 프레임 다음 rAF에 같은 격자 시각을 줘 늦은 프레임으로 잡히지 않고, 목표를 낮춰도 가벼운 프레임은 일찍 보여 무거운 프레임만 늦게 보이는 것은 그대로다(6.6, DECISIONS 12절)
- **격자 끄기(`?camSnap=0`).** 맵 스크롤 어긋남 p95가 0.47 → 0.04px(백버퍼)다. 시야 빛 톱니(22px)보다 훨씬 작아 기본은 그대로 둔다(HUMAN_CHECKS에서 실기기로 견줌)

### 6.5 내 빛 따라가기: 실제 셰이더 화소 (`tests/e2e/fog-follow.webgl.spec.ts`)

pacing 표의 ⑤는 렌더러가 넘긴 값(안개 주기 눈 + 옮긴 양)이라 셰이더가 정말 그렇게 그렸는지는 화소로 따로 잰다. WebGL(SwiftShader) 생존자 품질 중간 144Hz(가상 시계)에서 걷는 동안 프레임마다 빛 지도를 읽어, 밝기 비를 'x만큼 옮긴 빛' 식에 최소 제곱으로 맞춰 실제로 그린 빛 중심을 찾고 지금 내 자리와 견준다. 같은 빌드에서 디버그 훅 `setFogFollowDisabled(true)`로 예전 그림(Δ = 0)을 만든다.

| | 빛 중심 − 지금 내 자리 폭 (타일) | 1080p 품질 높음 (89.3px/타일) | 휴대폰 중간 (약 50px/타일) |
|---|---|---|---|
| 따라가기 끔 (예전 그림) | 0.243 | 21.7px | 12.3px |
| 따라가기 켬 | 0.006 | 0.5px | 0.3px |

- 시험 조건: 끔 > 0.15타일, 켬 < 0.05타일. 생존자 높음 · 괴물은 경계 노이즈 · 딱 잘린 빛이라 비를 맞추기 어려워 '앞은 밝아지고 뒤는 어두워진다'(괴물 근접 원 앞 띠 비 2.7~2.9, 뒤 0.30~0.35)만 본다
- 실제 GLSL과 단위 시험의 TS 쌍둥이(`followTexel`)를 크롬에서 같은 빛 지도로 돌려 차이 최대 0. 겹친 팀원 빛 모형 오차 0.172(첫 구현) → 0.003, 괴물 돌진 중 Δ가 0으로 돌아가는 프레임 44~47회(첫 구현 한도 0.5) → 0회(`monsterFollowMax` 0.667)

### 6.6 안개 주기 프레임 비용 (남은 후보, 진단만)

걷는 동안 안개 주기 프레임(빛 지도를 다시 칠한 프레임 — 생존자 50ms · 괴물 1/30초마다)과 그 밖 프레임의 메인 스레드 작업(rAF 콜백 안 시간, `perfHooks`)을 따로 쟀다. 실제 시계 · 헤드리스 60Hz · 봇과 연습(봇 움직임), 좌우로 1.8초씩 네 번 걷기. 같은 컨테이너에서 고치기 전(ea25bcf) → 최종 빌드를 이어서 쟀다.

- 안개 프레임이 다른 프레임의 3.5~5.8배다. 144Hz(6.9ms)에서 그 프레임만 vsync를 넘기면 1초에 20번 한 칸 늦게 보인다 — 크롬은 다음 rAF에 같은 격자 시각을 줘 FPS · 늦음에는 안 나온다(6.1). 가상 시계 '안개 프레임만 넘침' 부하가 이것의 모형이고, 목표를 낮춰도 줄지 않는다(6.3)
- CPU 프로필(압축하지 않은 빌드, WebGL 높음 걷기): 안개 주기 비용의 대부분이 빛 지도 텍스처 올리기 `texImage2D`(1초에 80ms = 주기마다 약 4ms)다. 이 컨테이너는 GPU가 없어 2D 캔버스를 CPU로 칠하고 올리기가 화소 복사다. 실제 크롬은 2D 캔버스를 GPU로 칠해 올리기가 GPU 안 복사라 훨씬 작다고 본다. JS(레이캐스트 · 빛 칠하기 기록 · 테두리 · 조각)는 주기마다 약 1ms, 미니맵 바닥 다시 그리기(안개 다음 프레임)가 따로 있다
- 내 빛 따라가기가 안개 프레임을 0.8~1.0ms 늘렸다(WebGL 생존자: 반경 r + 0.5 레이캐스트 · 넓은 다각형 칠하기). Canvas 경로는 그대로
- 실기기 값을 몰라 안개 일을 나누지 않고, `?debug=1`에 '넘김 %'(vsync 안에 못 끝낸 프레임) · '안개 p95'를 더했다(DECISIONS 12절, HUMAN_CHECKS). 측정 스크립트는 저장소에 넣지 않았다(한 번 쓰는 진단)
